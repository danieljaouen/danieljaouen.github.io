Virtual machines#

Lepton runs virtual machines with QEMU, Alpine's build, installed on demand. Machines are arm64 guests (Lepton itself, or any arm64 Linux), run headless on their serial consoles, much as UTM runs them on a Mac.

sudo app install qemu                     # QEMU, qemu-img, UEFI firmware (about 31 MB)
vm create test -i ~/lepton.iso            # a machine booting Lepton's ISO
vm start test -c                          # start it, and attach its console

At full speed: nested virtualization#

A machine runs at the CPU's speed when Lepton has KVM (/dev/kvm). Lepton's kernel has KVM, but it needs the CPU's virtualization mode, which Lepton only gets when it runs in a VM that passes it on: nested virtualization. Macs with an M3 or later chip have it, on macOS 15 or later.

  • With mix lepton.qemu, add --nested. It boots Lepton's kernel directly, because the UEFI firmware hangs in that mode under macOS's Hypervisor.framework. The clock is then set by ntpd a few seconds after the network comes up.
  • In UTM, nested virtualization needs the QEMU machine option virtualization=on and booting from the kernel image (vmlinuz, initrd.img, and the command line in grub.cfg, all on the ISO).

Without KVM, QEMU emulates the CPU: machines still run, many times slower. vm info NAME says which.

Managing machines#

CommandWhat it does
vmlist your machines
vm create NAME [-m MB] [-c CPUS] [-s SIZE] [-i ISO] [-f HOST:GUEST]make one (2048 MB, 2 CPUs, a 16G disk by default)
vm start NAME [-c]start it (-c: attach its console)
vm console NAMEits serial console; C-] detaches, the machine keeps running
vm log NAMEwhat its console printed lately
vm stop NAME [-f]press its power button (-f: end it at once)
vm set NAME KEY=VALUE...change memory, cpus, iso, forward
vm info NAME / vm delete NAMEsettings and state / remove it

A machine is a directory, ~/VMs/NAME, with its settings in vm.toml and its disk in disk.qcow2. The disk grows as the guest writes to it. Machines run as you, and keep running after the terminal that started them closes.

Each machine gets UEFI firmware, a virtio disk, the CD (booted first, while iso is set: vm set NAME iso= takes it out after installing), user-mode networking, and a serial console. The guest reaches the network, and this machine at 10.0.2.2. To reach the guest, forward a port: with vm set test forward=2222:22, ssh -p 2222 root@localhost reaches the guest's sshd.

Testing Lepton inside Lepton#

With QEMU installed, mix lepton.qemu works in a checkout of Lepton's source, in Lepton. It finds QEMU on the path of Lepton's mix, and of Claude Code's bash:

git clone https://github.com/danieljaouen/lepton && cd lepton
mkdir -p out && curl -o out/lepton.iso https://github.com/danieljaouen/lepton.iso/releases/latest/download/lepton.iso
mix compile
mix lepton.qemu --test          # the self-test suite, in a VM inside Lepton

With KVM, the suite takes about as long as it does on the Mac.

Building and publishing Lepton from Lepton#

The whole cycle works inside Lepton, with sudo app install qemu mix-tools (mix-tools brings git, and tar, xz and zstd for the build's sources). Lay the repositories out as on the Mac, side by side:

cd ~/src
git clone --recurse-submodules https://github.com/danieljaouen/lepton.git
git clone https://github.com/danieljaouen/danieljaouen.github.io.git
git clone https://github.com/danieljaouen/lepton.iso.git
cd lepton
mix lepton.iso && mix lepton.qemu --test && mix lepton.publish

That builds the ISO from its sources (about 1 GB to download the first time), runs its self-tests in a VM, and only if they pass, publishes the release and the site. Mix runs in a VM of its own, which Lepton treats as a program, not as the OS: Lepton's application started there (to generate the docs) runs as it does on a Mac, without a second copy of the system's services.

  • The ISO installs a dotfiles repository into /root: the one on GitHub (danieljaouen/dotfiles, fetched at each build, so a build here matches one on the Mac), or a local checkout that LEPTON_DOTFILES names.
  • Publishing needs a GitHub token, in GH_TOKEN, and pushes over HTTPS. Point git at it with a GIT_ASKPASS script that prints x-access-token for the user name and the token for the password.
  • Commits need your name and email: GIT_AUTHOR_NAME, GIT_AUTHOR_EMAIL (and GIT_COMMITTER_...), or user.name and user.email in ~/.gitconfig.
  • On the live ISO all of this is kept in memory: give the VM 6 GB or more.

Limits#

  • No display: machines run on their serial consoles. Lepton as a guest works fully there; a desktop guest's screen isn't shown.
  • arm64 guests only (qemu-system-aarch64).
  • vm is Lepton's own command: native programs, Claude Code's bash among them, run it as lepton vm ...; vm console needs a terminal.
